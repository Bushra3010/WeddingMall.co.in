## Authorisation helper functions

All are `SECURITY DEFINER` with `set search_path = ''`, and `STABLE` so the planner caches them per statement. They are `SECURITY DEFINER` specifically so a policy *on* a membership table can call them without recursing into its own policy.

| Function | Returns | Used by |
|---|---|---|
| `has_admin_permission(text)` | boolean | every admin-gated policy |
| `is_admin()` | boolean | admin catalogue reads |
| `vendor_role_of(uuid)` | `vendor_role` | membership resolution |
| `is_vendor_member(uuid)` | boolean | vendor-scoped reads |
| `vendor_can(uuid, text)` | boolean | vendor-scoped writes |
| `can_access_enquiry(uuid)` | boolean | enquiry, conversation, message, attachment policies |

`vendor_can()` mirrors `VENDOR_ROLE_CAPABILITIES` in `src/lib/permissions/catalogue.ts`. **Changing one without the other is a security defect** — see ADR-004.

## RLS posture

RLS is enabled on **every** table in `public`. Deny by default: a table with no matching policy is unreadable.

| Resource | Guest | Customer | Vendor member | Admin |
|---|---|---|---|---|
| `public_vendors` view / active vendors | read | read | read | read |
| Vendor draft listing | — | — | own vendor by membership | `listing.moderate` |
| `profiles` | — | own | — | `user.support` |
| `shortlists` | — | own CRUD | — | **no access by default** |
| `enquiries` | — | own | own vendor | `lead.read` / `lead.assign` |
| `messages` | — | own thread | own vendor thread | `lead.read` |
| `enquiry_notes` (internal) | — | **never** | own vendor | `lead.read` |
| `reviews` | approved only | own + create | approved + respond | `review.moderate` |
| `vendor_documents` | — | — | owner/manager | `vendor.verify` |
| `audit_logs` | — | — | — | `admin.manage` |
| `webhook_events` | — | — | — | **service role only** |

Tables with **no write policy at all**, by design:

- `enquiry_events` — append-only; no update or delete path exists.
- `audit_logs` — immutable; written by the service-role client only.
- `admin_memberships` — no insert/update/delete policy, so privilege escalation cannot happen through PostgREST. Admin elevation is a service-role job with an audit entry (Epic E: "super-admin role cannot be created through public input").
- `user_consents` — insert-only; consent history is an audit trail.
- `webhook_events` — service role only.

## Storage buckets

| Bucket | Public | Path convention | Write gate |
|---|---|---|---|
| `vendor-media` | yes | `<vendorId>/<file>` | `vendor_can(…, 'media.manage')` |
| `review-media` | yes | `<userId>/<file>` | own user id |
| `vendor-documents` | **no** | `<vendorId>/<file>` | `vendor_can(…, 'team.manage')`; read also `vendor.verify` |
| `message-attachments` | **no** | `<enquiryId>/<file>` | `can_access_enquiry()` |

Private buckets are read through short-lived signed URLs issued server-side after a permission check — never linked directly.

The first path segment is the tenant id, and policies cast it with `((storage.foldername(name))[1])::uuid`. **Uploads must therefore write to exactly that layout**; a malformed path will raise a cast error rather than silently granting access, which is the intended failure direction.

## Notable constraints and indexes

- `enquiries (customer_id, idempotency_key)` unique where key is not null — idempotent submission (PRD 10.3).
- `webhook_events (provider, external_event_id)` unique — webhook idempotency (Epic F).
- `shortlists (user_id, vendor_id)` unique; `reviews (enquiry_id, customer_id)` unique.
- `vendor_categories (vendor_id)` unique where `is_primary` — exactly one primary category.
- `vendor_media (vendor_id)` unique where `is_cover` — exactly one cover image.
- `vendor_service_areas` uses two partial unique indexes rather than a composite primary key, because `area_id` is nullable (whole-city coverage) and Postgres forbids NULL in a primary key.
- Trigram GIN indexes on `vendors.display_name`, `vendors.search_text`, `cities.name`, `categories.name`.
- `vendors.search_tsv` is a generated column over `search_text`, refreshed by triggers on listings, categories, and packages.

## Rating aggregation

`reviews_refresh_rating` recomputes `vendors.rating_average` and `rating_count` from **approved reviews only**, on insert, on status/rating update, and on delete. The trigger function branches on `TG_OP` because `NEW` is unassigned in a DELETE trigger.

## Search contract

`search_vendors(filters jsonb)` returns a fixed row shape including `rank_score` and a windowed `total_count`. Keep the shape stable: `src/server/dal/search.ts` is the adapter boundary, and an external engine should be swappable behind it without touching callers (PRD 11.3).

Ranking weights follow PRD 6.2 exactly. `rating_confidence` uses Bayesian shrinkage — see ADR-005.

**`search_vendors` is `SECURITY DEFINER` and therefore bypasses RLS** — see ADR-006 before modifying it.

## Local workflow

```bash
supabase start          # boots Postgres, Auth, Storage, Studio
npm run db:reset        # re-applies all migrations, then seed.sql
npm run db:types        # regenerates src/types/database.ts
```

To create a local admin (there is no public admin sign-up, per PRD 6.4):

```sql
-- after signing up through the UI, in Studio's SQL editor
insert into public.admin_memberships (user_id, role_id, status)
select u.id, r.id, 'active'
from auth.users u, public.admin_roles r
where u.email = 'you@example.com' and r.code = 'super_admin';
```
